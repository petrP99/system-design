# ***Генерация ID***

В платежной системе мы внедряем единый подход к генерации идентификаторов на основе UUIDv7(далее UUID) для всех основных
бизнес-сущностей. Этот выбор обусловлен требованиями к глобальной уникальности, временной упорядоченности и отсутствию
узких мест в распределенной архитектуре.

* содержат временную метку, что позволяет сортировать платежи по времени без дополнительных полей.
* в отличие от Snowflake, не требует распределения worker ID через централизованный сервис
* поддерживается в современных библиотеках, что упрощает внедрение.

***

## Процесс перехода

* В Payments DB
  UUID становится первичным ключом в таблице payments
  Все внешние ссылки на платежи используют его
  В таблице outbox используется UUID для обеспечения идемпотентности отправки событий
  Генерация происходит на уровне Payments Service при создании платежа

* В Wallet (связь платежей с движениями по кошельку)
  В таблице transactions добавлено поле payment_id UUID
  Это позволяет легко связывать операции в кошельке с платежами
  При обработке события создания платежа из Kafka Wallet Service использует UUID для:
  Поиска соответствующей блокировки/списания средств/создания записи в истории транзакций
* В событиях Kafka
  Каждое событие содержит payment_id, используется для идемпотентной обработки событий
* В логах и трассировке (correlation id)
  UUID используется как основной correlation_id во всех логах
  Это позволяет легко отслеживать запрос через все сервисы с помощью единого идентификатора

## Последствия перехода с sequence на UUID

### Влияние на индексы и производительность

Размер ключа: увеличение с 8 байт до 16 байт
Рост размера индекса
Производительность: незначительное снижение скорости вставок из-за большего размера ключа
Плюсы: компенсируется хорошей аллокацией всех последующих вставок в индекс (за счет сортировки, они будут прирастать "справа")

### Влияние на интеграции

Старые ID: будут храниться в поле legacy_id для обратной совместимости с Core Banking
Внешние API:
Новые интеграции используют UUID как основной идентификатор
Для старых интеграций реализован mapping через Anti-Corruption Layer(Adapter)
Партнеры получают UUID, но могут запросить legacy_id при необходимости
Core Banking: получает legacy_id через ACL, который преобразует UUID в sequence

### Миграция данных

Существующие платежи:
Для всех существующих платежей будет сгенерирован UUID 
Переходный период: Система поддерживает оба формата (UUID и legacy_id)
Все новые платежи используют только UUID
Старые ID сохраняются только для обратной совместимости с Core Banking
Двоичная совместимость не требуется, так как все новые платежи используют UUID, а старые ID хранятся только для legacy
