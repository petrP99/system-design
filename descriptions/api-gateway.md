## API Gateway

На входе система имеет **Kong Gateway**, выполняющий аутентификацию пользователей по **JWT**, лимитирует запросы и маршрутизирует их в соответствующие сервисы.

### Почему выбран Kong:
*   **Готовые плагины и производительность**: Высокая скорость на базе **Nginx**, не требующая специальных знаний при настройке.
*   **Языковая независимость**: Отсутствие потенциальных проблем в случае переписывания микросервисов на другие языки (в отличие от *Spring Cloud Gateway*).

---

### Риски

#### Архитектурные риски
*   **Зависимость от базы данных**: Kong требует **PostgreSQL/Cassandra** для хранения конфигурации.

#### Эксплуатационные риски
*   **Производительность с большим количеством плагинов**: Каждый плагин добавляет задержку.
*   **Дефицит экспертов**: Меньше специалистов по Kong по сравнению с классическим NGINX.

---

### Обоснование выбора
Несмотря на риски, выбор **Kong** оправдан для платежной вертикали по следующим причинам:

1.  **Сокращение времени разработки**: Готовые плагины экономят 3-6 месяцев разработки собственного решения на базе NGINX.
2.  **Гибкость для будущего развития**: Поддержка новых протоколов и стандартов без полной замены шлюза.
3.  **Сквозная трассировка**: Критично для отладки платежных операций через несколько систем.
