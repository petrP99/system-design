# ***Генерация ID***

В платежной системе мы внедряем единый подход к генерации идентификаторов на основе UUIDv7(далее UUID) для всех основных
бизнес-сущностей. Этот выбор обусловлен требованиями к глобальной уникальности, временной упорядоченности и отсутствию
узких мест в распределенной архитектуре.

* содержат временную метку, что позволяет сортировать платежи по времени без дополнительных полей.
* в отличие от Snowflake, не требует распределения worker ID через централизованный сервис
* поддерживается в современных библиотеках, что упрощает внедрение.

***

## Процесс перехода

* Добавлено новое поле dual_id UUIDv7
  legacy_id (sequence) остается первичным ключом
  Все новые сервисы используют dual_id как сквозной идентификатор
  В таблице outbox используется dual_id для обеспечения идемпотентности отправки событий
  Генерация dual_id происходит на уровне Payments Service при создании платежа

* В Wallet (связь платежей с движениями по кошельку)
  В таблице transactions добавлено поле legacy_dual_id UUID
  Это позволяет легко связывать операции в кошельке с платежами
  При обработке события создания платежа из Kafka Wallet Service использует dual_id для:
  Поиска соответствующей блокировки
  Списания средств
  Создания записи в истории транзакций

* В событиях Kafka
  Каждое событие содержит legacy_dual_id, используется для идемпотентной обработки событий
  Поле legacy_id сохраняется для обратной совместимости
* В логах и трассировке (correlation id)
  UUID используется как основной correlation_id во всех логах
  Это позволяет легко отслеживать запрос через все сервисы с помощью единого идентификатора

***

## Последствия перехода с sequence на UUID

### Влияние на индексы и производительность

Размер ключа: увеличение с 8 байт до 16 байт
Рост размера индекса
Производительность: незначительное снижение скорости вставок из-за большего размера ключа

Плюсы:

* Хорошая локальность вставок благодаря временной упорядоченности UUID
* Нет необходимости перестраивать существующие индексы
* Постепенный переход без перезаписи первичных ключей

### Влияние на интеграции

legacy_id (sequence) сохраняется как первичный ключ
Используется только для интеграции с Core Banking через ACL
Внешние API:
Новые интеграции используют dual_id (UUID) как основной идентификатор
Для старых интеграций сохраняется поддержка legacy_id
Партнеры получают dual_id, но могут запросить legacy_id при необходимости
Core Banking: получает legacy_id через ACL, который преобразует dual_id в sequence

### Миграция данных

* Существующие платежи:
  Не переписываем первичные ключи - legacy_id остается PK
  Добавляем новое поле dual_id в таблицу платежей
  Не генерируем UUID для старых платежей - поле остается NULL для существующих записей
  Период двойного использования (dual-id):
  Система поддерживает оба формата идентификаторов
  Все новые платежи генерируют оба ID:
  legacy_id (sequence) - для совместимости с legacy
  dual_id (UUID) - как основной сквозной идентификатор
  Новые сервисы работают с dual_id
  Старые сервисы продолжают работать с legacy_id
