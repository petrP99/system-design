# Платёжная платформа: Микросервисная архитектура v2.0

Репозиторий содержит комплект архитектурной документации по трансформации платежной системы в распределенную событийно-ориентированную платформу. 
Проект демонстрирует реализацию отказоустойчивой обработки платежей с использованием паттернов **Saga**, **Transactional Outbox** и **CQRS**.

## Цели и задачи архитектуры

Цель проекта — создание масштабируемой системы обработки платежей со следующими характеристиками:
* **Распределенная транзакционность**: Управление жизненным циклом платежа через **Saga (Оркестрация)**.
* **Гарантированная доставка**: Использование **Transactional Outbox (Debezium)** для исключения потери событий.
* **Высокая производительность чтения**: Разделение Write-модели и Read-модели (**CQRS**) с использованием **ClickHouse**.
* **Изоляция внешних систем**: Выделенный **Callback Service** для приема уведомлений от провайдеров.

---

## Стратегический уровень (Patterns)

### 1. Saga Orchestration
Центральный компонент **Orchestrator** координирует цепочку вызовов:
1. **Wallet Service**: Синхронный резерв средств (`reserveFunds`).
2. **Transaction Service**: Асинхронная инициация внешнего платежа.
3. **Финализация**: Подтверждение (`confirm`) или компенсация (`release`) при ошибке/таймауте.

### 2. Transactional Outbox & CDC
Для обеспечения атомарности операций (изменение состояния + отправка события) используется:
* Таблицы `wallet_outbox` и `tx_outbox` в PostgreSQL.
* **Debezium** как внешний Worker, считывающий WAL лог и публикующий события в Kafka.

### 3. CQRS Read-Model
* **Write Path**: PostgreSQL в сервисах Wallet и Transaction (нормализованные данные).
* **Read Path**: **Payment Query Service** + **ClickHouse**. Денормализованная проекция `payment_view` для мгновенной выдачи истории платежей.

## Ключевые технические решения

1. **Идемпотентность**: Реализована на уровне БД через `Unique Constraint` по глобальному `payment_id` во всех пишущих сервисах.
2. **Callback Handling**: **Callback Service** изолирует систему от внешних HTTP-вызовов, валидирует подписи и перекладывает результат в gRPC/Kafka.
3. **Аналитика**: Выбор ClickHouse для Read-модели позволяет хранить миллиарды транзакций и выполнять аналитические запросы без деградации производительности основной системы.
